# fix: Discovery returns nothing after specs 005-008 refactor

## Summary

Fix the job discovery feature that silently fails or hangs when users click "Run Discovery." Three changes: eliminate the `requests` external dependency (stdlib `urllib` instead), kill the URL verification bottleneck that blocks discovery for 10+ minutes, and dispatch the subprocess asynchronously so the API returns immediately while work continues in the background.

## Problem Frame

After specs 005-008 refactored the tracker server from `ThreadingHTTPServer` to `HTTPServer` and from async `Popen` to synchronous `subprocess.run()`, discovery regressed in three ways:

1. **`ModuleNotFoundError`** — `scripts/discover_jobs.py` imports `requests`, which only exists inside the venv. If the server is started manually (`python3 serve_tracker.py`) rather than through `JobQuest.command` (which activates the venv), the subprocess crashes before any search runs.

2. **Timeout during URL verification** — `verify_job_urls()` HEAD-checks every new URL at 5s each. With an empty or near-empty queue, 350+ extracted jobs × 5s = 1750s of blocking I/O. The committed `subprocess.run(timeout=180)` kills the subprocess mid-verification. No jobs are written.

3. **Bare QUEUE_TEMPLATE** — the committed 12-line template has no `const JOBS = []` array, so `append_to_queue()` cannot write results when the queue is reset. (Already fixed in the working tree via a 490-line template.)

The cumulative effect: users click "Run Discovery," the modal shows "⏳ Running discovery…", the browser's `fetch()` times out after 60–120s, and no results appear.

## Requirements

- R1. Discovery runs successfully regardless of whether the server was started inside the venv — no `ModuleNotFoundError` from missing `requests`
- R2. The discovery API returns a response within 3 seconds, showing "running" status immediately rather than blocking for minutes
- R3. URL verification is removed from the discovery flow — no more HTTP HEAD checks bottlenecking results
- R4. All 189 tests continue to pass (186 committed + 3 new from the working tree)

## Scope Boundaries

- Out of scope: Restoring the full streaming-log UI from before specs 005-008 (polling endpoint replaces the old animated `<div id="discovery-log">`)
- Out of scope: Changing the Exa query catalog or adding new job boards
- Out of scope: Adding error recovery or retry logic beyond what already exists in `exa_search()`

## Context & Research

### Relevant Code and Patterns

- `serve_tracker.py` — HTTP server with `TrackerHandler(SimpleHTTPRequestHandler)`. Docstring claims "Zero dependencies beyond Python stdlib." Already imports `urllib.parse` for URL normalization in `_check_url()`.
- `scripts/discover_jobs.py` — standalone script with `exa_search()`, `verify_job_urls()`, `append_to_queue()`, `main()`. Only user of the `requests` module.
- `web_ui.py` — uses `subprocess.Popen` + `threading.Lock` for background pipeline dispatch. This is the codebase's threading precedent to follow.
- `data/job_queue.html` — HTML with embedded `const JOBS = [...]`. Generated by `append_to_queue()` which regex-replaces the JOBS array in-place.

### Institutional Learnings

- **`verify_job_urls()` is self-documented as optional.** The function's own revert note (line 454) reads: *"if this causes jobs to be lost or slows discovery too much, delete the verify_job_urls() function and remove the call in main(). The pipeline worked fine without it."* It kills 86% of valid URLs because LinkedIn, StepStone, and Join.com all block HEAD requests.
- **The `requests` dependency was a bypass of pi's broken `web_search` tool**, not casual dependency creep. Replacing it with `urllib` aligns with the server's stated stdlib-only constraint.

### External References

- Not applicable — the fix is internal to the codebase, no external docs needed.

## Key Technical Decisions

- **`urllib.request` replaces `requests`:** The Exa API call is a single `POST` with JSON body and API-key header — trivial with stdlib. The server already imports `urllib.parse`, so no new stdlib modules are introduced. This eliminates the venv dependency for the discovery subprocess.
- **Kill `verify_job_urls()` entirely:** The function kills 86% of valid URLs and is the bottleneck (350 URLs × 5s timeout). The Exa API's `startPublishedDate` filter already constrains results by recency, making the HEAD check redundant filtering. Keep the function definition with a deprecation docstring for documented reversibility.
- **`subprocess.Popen` + daemon `Thread` replaces `subprocess.run`:** Follows the pattern from `web_ui.py`. The API returns immediately with `{status: "running"}`. A polling endpoint (`GET /api/discover/status`) lets the frontend track progress. No need for `ThreadingHTTPServer` — the server stays single-threaded for normal requests; the daemon thread only handles the subprocess lifecycle.

### U3. Dispatch discovery subprocess in background, add polling endpoint

**Goal:** The discovery API returns immediately with "running" status instead of blocking for the full subprocess duration.

**Requirements:** R2

**Dependencies:** U2 (URL verification removal ensures the subprocess itself finishes in under 30 seconds)

**Files:**
- Modify: `serve_tracker.py` (`_discover_jobs()` handler, `QUEUE_TEMPLATE` JS, module-level imports)
- Test: `tests/test_tracker.py` (add async dispatch tests)

**Approach:**
- Add `import threading` and `import time` to the module-level imports
- Add module-level state with a lock:
  - `_discovery_lock = threading.Lock()` guards `_discovery_status` dict
  - `_discovery_status = {"running": False, "jobs_found": 0, "error": None, "started_at": 0}`
- In `_discover_jobs()`: validate request → if already running return `{"ok": false, "error": "Discovery already in progress"}` → set `_discovery_status["running"] = True` → spawn `threading.Thread(target=_run_discovery, args=(mode, clear), daemon=True)` → return `{"ok": true, "status": "running"}` immediately
- Add `GET /api/discover/status` endpoint returning the current `_discovery_status` dict
- The daemon thread runs subprocess, updates `_discovery_status` under lock upon completion (success → `jobs_found`, error → `error`), sets `running = False`
- Update `QUEUE_TEMPLATE` JS: after `POST /api/discover` returns, poll `GET /api/discover/status` every 2 seconds. When `done: true`, show result count and reload. On error, show the error message
- Follow the `web_ui.py` Popen + Lock pattern for process lifecycle management

**Technical design:** (directional guidance, not implementation specification)

```
# serve_tracker.py — module-level state
_discovery_lock = threading.Lock()
_discovery_status = {"running": False, "started_at": 0, "jobs_found": 0, "error": None}

def _run_discovery(mode, clear):
    """Run in daemon thread. Updates _discovery_status on completion."""
    try:
        if clear: _reset_queue_file()
        result = subprocess.run([sys.executable, str(script), "--mode", mode],
                                capture_output=True, text=True, timeout=600,
                                cwd=str(PROJECT_ROOT))
        # ... parse result, count jobs ...
        with _discovery_lock:
            _discovery_status["jobs_found"] = jobs_found
            _discovery_status["running"] = False
    except Exception as e:
        with _discovery_lock:
            _discovery_status["error"] = str(e)
            _discovery_status["running"] = False

# GET /api/discover/status → {"running": bool, "jobs_found": int, "error": str|null}
```

**JS polling pattern** (QUEUE_TEMPLATE):
```
startDiscovery() → POST /api/discover → receive {ok, status: "running"}
  → poll loop: setInterval every 2s → GET /api/discover/status
    → if running: update status text "⏳ Searching…"
    → if error: stop polling, show "❌ {error}"
    → if done: stop polling, show "✅ Found N jobs! Reloading…", location.reload()
```

**Patterns to follow:**
- `web_ui.py` `Popen` + `Lock` + background thread for process lifecycle
- Existing `TrackerHandler` do_GET/do_POST routing pattern for the new status endpoint

**Test scenarios:**
- Happy path: `POST /api/discover` returns `{"ok": true, "status": "running"}` within 3 seconds
- Happy path: `GET /api/discover/status` returns `{"running": true}` while discovery is in progress
- Happy path: `GET /api/discover/status` returns `{"running": false, "jobs_found": N}` after discovery completes
- Edge case: `POST /api/discover` returns error when discovery is already running
- Integration: Full end-to-end — start discovery, poll status, verify queue file has new jobs after completion
- Error path: `GET /api/discover/status` returns `{"running": false, "error": "…"}` when discovery fails
- Error path: `POST /api/discover` with invalid mode returns 400 error
- Existing: `test_clear_queue_template_is_parseable` still passes (QUEUE_TEMPLATE still has `const JOBS = [`)

**Verification:**
- `pytest tests/test_tracker.py -v` — all tests pass
- `pytest tests/ -v` — all 189+ tests pass
- Manual: click "Run Discovery" in browser, modal shows "⏳ Running…", status updates within 2 seconds, page reloads with new jobs after subprocess completes
- Manual: `curl -s http://127.0.0.1:7880/api/discover/status` returns valid JSON while discovery runs

## System-Wide Impact

- **Interaction graph:** `_discover_jobs()` no longer blocks the HTTP request cycle. Other endpoints (`/api/applications`, `/`, `/queue`) remain responsive during discovery.
- **Error propagation:** Background errors surface through `/api/discover/status` → frontend status text. No silent failures — errors are always visible as `"❌ {error}"` in the modal.
- **State lifecycle risks:** `_discovery_status` shared between thread and main — guarded by `_discovery_lock`. No concurrent discovery runs allowed (gated by `running = True` check under lock).
- **Unchanged invariants:** `_reset_queue_file()`, `_recompile_pdf()`, `_check_url()`, and `_serve_json()` behaviors are unchanged. The tracker page, PDF recompile, and URL check continue to work identically.

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| `urllib.request.urlopen` behaves differently from `requests` for Exa API (encoding, error handling) | Test with real Exa calls (`--max-per-query 2`) before relying on the full run; the existing `exa_search` function already has error handling for HTTP failures |
| Background thread writes to queue file while frontend reads — race condition | The discovery subprocess writes atomically via `append_to_queue()` (replaces JOBS array in the HTML string, writes in one `write_text()` call). Read is optimistic — the browser polls for completion before reloading |
| Two concurrent discovery requests could corrupt state | Gated: `_discover_jobs()` checks `_discovery_status["running"]` under lock and returns error if already running |
